The Installer Matrix: Testing the Wild West of Windows Packaging Before It Hits Cloud

We're building a tool that automates Windows application packaging for Intune. Before scaling it to cloud, we forced ourselves through a disciplined local matrix — 30 installer types, 9 buckets, deliberately adversarial samples. Here's what we built, what we broke, and the bugs we caught before they became production failures.

01 What a Packaging Engineer Does Today — Without This Tool

Windows application packaging for Intune is one of those jobs that looks simple until you're inside it. The surface area is deceptive. Every vendor makes different choices. Every installer framework has its own silent-install convention, its own exit code semantics, its own opinions about where to write registry keys. And none of them are consistent across versions.

Here's what a packaging engineer actually does, manually, to produce a single deployable .intunewin:

// manual packaging — the old way
Download the installer, inspect filename/extension, guess the framework
Look up silent flags in vendor docs (often outdated) or from memory
Run the installer with candidate flags, observe whether a UI appeared
Poke around the registry and Program Files for detection anchors
Write the install script by hand, wrap with IntuneWinAppUtil.exe
Upload to Intune, deploy to test device, find out the detection rule was wrong, start over
// pkgprobe — one job
Upload the installer
Subtype detection classifies the framework with confidence score
VM trace runs the installer silently, ProcMon captures everything
Registry diff produces verified detection candidates with confidence scores
Download a .intunewin with correct silent args, PSADT wrapper, and detection rules already baked in

The output is a self-contained, ready-to-deploy package. No research. No trial-and-error. No rewrapping. The hard part — figuring out how the installer actually behaves at runtime — is done automatically against a real VM.

02 Why We Built the Installer Matrix Before Touching Cloud

We had a working local trace pipeline and a tempting question: why not just scale it to cloud now? More VMs, more parallelism, automated orchestration. The answer is that cloud multiplies operational surface area — credentials, quotas, VM provisioning, egress, retry semantics — without proving that the core logic behaves correctly across diverse real-world payloads. A bug in silent-switch selection that slips through local testing becomes a bug that fires across hundreds of concurrent cloud jobs.

The right move was a disciplined local matrix first. Run the full range of installer types, subtypes, and adversarial edge cases against a single trace VM. Capture artifacts. Understand failure modes. Then move to cloud, carrying those findings as a test baseline.

💡
The gate we set for ourselves

Move to cloud only once: (a) trace completes or fails with actionable artifacts across all installer types, (b) we have timeout defaults we're willing to defend in production, and (c) we understand wrapper verification cost per job under real load.

03 How the Codebase Partitions Installer Types

pkgprobe's switch policy isn't a flat list of flags to try. It's structured around a typed taxonomy that maps directly to how installers actually behave in the wild. Understanding the taxonomy is what makes the matrix meaningful rather than random sampling.

At the top level, installers split into MSI and EXE based on extension and file evidence. EXEs are further classified by ExeSubtype — the detection logic that decides which silent-switch policy to apply:

WiX Burn /quiet Bootstrapper chains, bundled runtimes, exit code 3010 high 4

Squirrel --silent Electron apps, per-user installs in %LocalAppData% high 3

MSIX wrapper Add-AppxPackage Different execution path entirely — not msiexec medium 1

The total target was 24–42 installers — enough to credential each bucket without trying to cover every vendor. This isn't a coverage exercise. It's a failure-mode exercise. Each installer was chosen because it exercises a specific known-difficult behavior, not because it's popular.

04 The Adversarial Cases — Where Things Get Interesting

Most installer testing stops at "did it run silently." That's not enough. The bugs that matter in production aren't the ones where an installer fails loudly — they're the ones where it succeeds in a way that's subtly wrong. Detection rule points to the wrong registry key. Exit code 1638 gets treated as a failure instead of "already installed." Silent install completes but spawns a background process that holds the installer service open.

We built eight specific adversarial cases into the matrix, each targeting a known failure mode:

⚠ case sensitivity
NSIS /S vs /s
Notepad++ NSIS requires uppercase /S. Lowercase /s silently fails to silent mode and presents a language picker — invisible under SYSTEM context, hangs indefinitely.
last_silent_args: /S ← correct
attempt: 1 / 3 ← first try
🔴 custom vendor flags
Mozilla Firefox -ms
Firefox's silent flag is -ms — not /S, not /quiet, not /silent. None of the standard generic EXE candidates work. The strongest test of the _GENERIC_EXE_BASE fallback ordering.
expected: -ms
generic fallback order tested
⚠ per-user installs
Squirrel / Electron apps
Discord, Slack, and GitHub Desktop all install into %LocalAppData%, not Program Files. Post-install detection that looks in the wrong place will always report not-installed.
install_path: %LocalAppData%\...
not: C:\Program Files\...
🔴 exit code semantics
VC++ Redist 1638
Returns exit code 1638 when a newer version is already installed. Some tools treat this as failure. The correct behavior is to treat it as success — the app is already there.
exit_code: 1638
meaning: already_installed → success
⚠ chain risk
Wireshark + Npcap
Wireshark's MSI bundles Npcap as a nested EXE. The trace needs to recognize and follow child processes, not just the primary installer. Silent flag for the outer installer may not propagate inward.
child_process: npcap-installer.exe
driver install: may prompt
✓ handled correctly
MSI / NSIS switch separation
Notepad++ ships both MSI and NSIS EXE for the same version. The trace correctly applied /qn to the MSI and /S to the EXE — the type detection branched correctly on the same underlying software.
npp.msi → /qn ✓
npp.exe → /S ✓
🔴 detection mismatch
7-Zip GUID discrepancy
Analysis read ProductCode {35222831…} from the MSI Property table. Post-install trace found {23170F69…} in the uninstall hive. Two different GUIDs — one of them would produce a broken Intune detection rule.
analysis: {35222831…}
trace: {23170F69…} ← conflict
ℹ different execution path
PowerShell MSIX
MSIX packages don't go through msiexec or a standard EXE — they require Add-AppxPackage. Detection needs to route to a completely different execution path. Easy to miss if MSIX coverage is thin.
exec: Add-AppxPackage
not: msiexec /i

05 A Bug We Caught Before It Shipped

The 7-Zip GUID mismatch wasn't a fluke — it exposed a real gap in how the pipeline handles MSI detection. The static analysis reads ProductCode from the MSI Property table before any install happens. The trace pipeline derives its detection candidate from what actually gets written to the Windows Installer uninstall registry hive after install completes. For most well-behaved MSIs these match. For 7-Zip, they didn't.

In production, this would have silently generated an Intune detection rule pointing at the wrong GUID. The app would deploy successfully and then immediately report as "not detected" — one of the most frustrating failure modes in Intune because it looks like a deployment failure rather than a detection rule problem.

🔴
What we shipped as a result

A new guardrail in both the OSS trace worker and the cloud API: when plan.metadata.ProductCode from analysis disagrees with the GUID extracted from the trace registry candidate, a structured warning is appended to verification_errors in the manifest — non-fatal, but visible. This runs on every MSI job now, not just the ones we happened to test.

// productcode mismatch guardrail — what we added
Analysis reads ProductCode from MSI Property table (static)
pkgprobe/analyzers/msi.py — stored in InstallPlan.metadata
pre-trace
Trace derives msi_product_code from post-install registry diff
pkgprobe_trace/manifest_builder.py — scans DiffResult.registry for Uninstall\ GUIDs
post-trace
New: compare both GUIDs, emit warning if they disagree
pkgprobe/msi_product_code_compare.py — shared helper, mirrored to API
guardrail
Warning surfaces in verification_errors — no hard failure, verified flag unchanged
Same schema field already present in the manifest, no new fields needed
non-fatal

The guardrail is intentionally non-fatal. Some MSIs legitimately write a different GUID than their Property table declares — it's unusual but real. The goal is visibility, not blocking. A packaging engineer who sees the warning knows to run Orca on the artifact and confirm which GUID is correct before deploying. Without the warning they'd never know until an endpoint reported detection failure.

07 Where We Are — Honest Progress Report

The matrix is still running. A few things worth being straight about:

What's working well. MSI and NSIS detection and switch selection are solid across everything we've tested. The PSADT wrapper path handles both families cleanly. Detection candidate generation — registry key, ProductCode, file_exists — is producing usable results with sensible confidence scoring. The end-to-end path from installer file to downloadable .intunewin is working.

Where there's still room to improve. The generic/unknown EXE bucket is the weakest area — it's the largest population in real-world deployments and the hardest to test systematically. The Firefox -ms case is a good example of the failure mode that matters there: a completely non-standard flag that no generic fallback list will ever enumerate. The right answer for that bucket is probably a combination of better heuristics and clearer surfacing of low-confidence cases to the user rather than silent guessing.

What we're not claiming. The matrix validates the type taxonomy and switch policy across representative samples. It doesn't tell us the failure rate against the full population of real-world enterprise installers — for that we need production traffic, which comes after the matrix, not instead of it. If 80% of enterprise software happens to fall into the generic EXE bucket (it probably doesn't, but if it did), the matrix wouldn't catch that.

🚀
The gate is: actionable artifacts, not green lights

The matrix isn't done when every installer passes. It's done when every failure — timeout, wrong flag, bad detection — produces a bundle that's diagnosable without re-running the job. That's the thing that makes cloud scale survivable.

// takeaway
Cloud doesn't fix a broken type matrix. It just makes the failures happen faster and further from your debugger.

The matrix didn't find every bug. It won't. What it did was force us to think about failure modes before we were debugging them at 2am across twelve cloud VMs with no local reproduction path. That's the protection we wanted in place before scaling.
